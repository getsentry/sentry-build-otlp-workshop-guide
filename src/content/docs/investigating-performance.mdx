## Understanding Performance in Distributed Systems

In a distributed application, a single user request might trigger:
- Frontend rendering
- API calls over the network
- Database queries
- Cache lookups
- External API calls (payment processing)

Traditional logging makes it hard to see the full picture. Distributed tracing shows you the entire flow with precise timing.

## Using Sentry Trace Explorer

Sentry's Trace Explorer allows you to search, filter, and analyze traces from your OpenTelemetry-instrumented application. With OTLP data, you can query spans using attributes, create visualizations, and identify performance bottlenecks.

<Aside type="tip">
**OTLP Tracing Capabilities**: When sending traces via OTLP, you can search and filter by span attributes, custom tags, and operation names. While you won't have all Sentry SDK features (like automatic performance issue detection), you get powerful query capabilities over your OpenTelemetry data.
</Aside>

## Scenario 1: Identifying Slow Database Queries

Your product search endpoint is occasionally slow. Let's use Trace Explorer to find the bottleneck.

<Steps>
1. **Navigate to Trace Explorer**

   In your Sentry project, go to **Explore** > **Traces**

2. **Filter for product search operations**

   Use the search bar to filter spans:

   ```
   span.op:db AND http.route:/api/products/search
   ```

   This shows all database operations that occurred during product search requests.

3. **Add performance metrics**

   Click **Add Series** and select:
   - `p90(span.duration)` - Shows 90th percentile duration (outliers)
   - `avg(span.duration)` - Shows average duration

   The chart will reveal performance trends over time.

4. **View span samples**

   Switch to the **Span Samples** tab below the chart. Sort by **Duration** (click the column header) to see the slowest queries.

5. **Inspect a slow span**

   Click on a Span ID to open the **Trace Waterfall View**. You'll see:
   - The complete request flow from frontend to database
   - Exact timing for each operation
   - Span attributes like `db.statement` showing the actual SQL query

   **Example attributes you'll find:**
   ```
   span.op: db
   db.system: postgresql
   db.statement: SELECT ... WHERE name ILIKE '%laptop%' OR description ILIKE '%laptop%'
   search.query: laptop
   search.results_count: 15
   ```

6. **Aggregate by database table**

   Switch to the **Aggregates** tab. Group by `db.table` to see which tables have the slowest queries:

   - Group by: `db.table`
   - Sort by: `p90(span.duration)`

   Click the stack icon next to any aggregate to see sample traces.
</Steps>

<Aside>
**What you learned**: The `ILIKE` operator on large text columns causes slow queries. Consider adding full-text search indexes or using a dedicated search service.
</Aside>

## Scenario 2: Analyzing Cache Performance

Are your cache hits effective? Let's measure cache hit rates and their performance impact.

<Steps>
1. **Search for cache operations**

   In Trace Explorer, search:

   ```
   span.op:cache.get
   ```

2. **Create a hit rate calculation**

   Group by `cache.hit` in the Aggregates tab:
   - `cache.hit:true` - Cache hits
   - `cache.hit:false` - Cache misses

   Compare the count of each to calculate your hit rate.

3. **Compare performance**

   Create two separate queries to compare:

   **Query 1 (Cache Hits):**
   ```
   span.op:cache.get AND cache.hit:true
   ```
   Add metric: `avg(span.duration)`

   **Query 2 (Cache Misses):**
   ```
   span.op:cache.get AND cache.hit:false
   ```
   Add metric: `avg(span.duration)`

   Cache hits should be significantly faster (< 5ms vs 100ms+ for database queries).

4. **Identify frequently missed keys**

   In Span Samples, filter for cache misses:
   ```
   span.op:cache.get AND cache.hit:false
   ```

   Look at the `cache.key` attribute to see which keys are missing most often.

5. **View the full request flow**

   Click a trace ID where `cache.hit:false`. In the waterfall, you'll see:
   - `cache.get` span (miss, ~2ms)
   - `db` span immediately after (query, ~150ms)
   - `cache.set` span (storing result, ~3ms)

   This shows the cache-aside pattern in action.
</Steps>

<Aside type="tip">
**Pro tip**: If you see low cache hit rates on product lists, check the `cache.key` values. The app uses `products:all` for the full list and `product:{id}` for individual products. High miss rates might indicate your cache TTL is too short or you're clearing cache too frequently.
</Aside>

## Scenario 3: Order Creation Performance Breakdown

Order creation involves multiple steps. Let's identify which step is the bottleneck.

<Steps>
1. **Filter for order creation traces**

   ```
   http.route:/api/orders AND http.method:POST
   ```

2. **View the waterfall**

   Click any Trace ID to open the waterfall view. You'll see a complete breakdown:

   ```
   └─ POST /api/orders (850ms)
      ├─ order.validate_user (45ms)
      │  └─ db SELECT users (42ms)
      ├─ order.validate_products (220ms)
      │  ├─ db SELECT products (38ms)
      │  ├─ db SELECT products (41ms)
      │  └─ db SELECT products (39ms)
      ├─ inventory.check (180ms)
      │  ├─ db SELECT products (55ms)
      │  ├─ db SELECT products (58ms)
      │  └─ db SELECT products (62ms)
      ├─ order.create_record (95ms)
      │  └─ db INSERT transaction (92ms)
      ├─ inventory.reserve (145ms)
      │  └─ db UPDATE transaction (140ms)
      └─ payment.process (250ms)
         └─ simulated payment gateway (248ms)
   ```

3. **Analyze the bottleneck**

   The waterfall reveals:
   - **Product validation** queries run sequentially (N+1 query problem)
   - **Payment processing** is the slowest single operation
   - **Database roundtrips** add up when ordering multiple items

4. **Correlate with order size**

   Use the search with span attributes:
   ```
   http.route:/api/orders AND order.items_count:>3
   ```

   Compare average duration for orders with different item counts:
   - 1 item: ~450ms
   - 3+ items: ~850ms

   This confirms the N+1 query problem.

5. **Examine span attributes**

   In the waterfall, click any span to see attributes:

   **Parent span (order.create):**
   ```
   order.user_id: 1
   order.items_count: 3
   order.total_amount: 459.97
   order.payment_method: credit_card
   order.status: confirmed
   ```

   **Child span (payment.process):**
   ```
   payment.order_id: 42
   payment.amount: 459.97
   payment.method: credit_card
   payment.status: success
   payment.transaction_id: txn_1234567890_abc123
   ```
</Steps>

<Aside>
**Optimization ideas**:
- Batch product queries into a single `WHERE id IN (...)` statement
- Consider async payment processing for non-critical paths
- Add Redis caching for frequently ordered products
</Aside>

## Scenario 4: Database Connection Pool Analysis

Are database connections becoming a bottleneck under load?

<Steps>
1. **Aggregate by database operation type**

   In Aggregates tab:
   - Group by: `db.operation`
   - Metric: `p90(span.duration)`

   You'll see aggregates for SELECT, INSERT, UPDATE operations.

2. **Find long-running transactions**

   Search for transactions that hold locks:
   ```
   db.transaction:true AND span.duration:>500ms
   ```

   Long-running transactions can cause connection pool exhaustion.

3. **Create a duration trend chart**

   Add series:
   - `avg(span.duration)` where `span.op:db`

   Look for spikes during high-traffic periods. If duration increases under load, you may need to increase connection pool size.

4. **Compare transaction vs single queries**

   **Query 1 (Transactions):**
   ```
   db.transaction:true
   ```

   **Query 2 (Single Queries):**
   ```
   span.op:db AND NOT db.transaction:true
   ```

   Transactions should be faster than the sum of individual queries (that's why we use them), but if they're slow, investigate lock contention.
</Steps>

## Setting Up Performance Alerts

Once you've identified performance patterns, create alerts to catch issues before users report them.

### How to Create Alerts

From any Trace Explorer query, click **Save As** > **Alert**. Configure the alert with:
- **Query**: The trace filter that identifies the operation
- **Metric**: What to measure (p95, avg, max duration)
- **Threshold**: When to trigger the alert
- **Action**: How to notify your team

### Recommended Performance Alerts

<Steps>
1. **Slow Order Creation**

   ```
   Query: http.route:/api/orders AND http.method:POST
   Metric: p95(span.duration)
   Threshold: > 1000ms
   ```

   **Why**: Order creation is a critical business flow. If it's consistently over 1 second, users will notice and abandon carts.

2. **Database Query Performance Degradation**

   ```
   Query: span.op:db AND db.table:products
   Metric: p90(span.duration)
   Threshold: > 200ms
   ```

   **Why**: Product table queries power your core catalog. Slow queries indicate missing indexes or query optimization issues.

3. **Cache Miss Rate**

   ```
   Query: span.op:cache.get
   Metric: count() where cache.hit:false
   Threshold: > 1000 per hour
   ```

   **Why**: High miss rates mean you're hitting the database unnecessarily. Check cache TTL or if cache is being cleared too frequently.

4. **Payment Processing Latency**

   ```
   Query: span.op:payment.process
   Metric: p95(span.duration)
   Threshold: > 500ms
   ```

   **Why**: Payment gateway slowness impacts conversion. May indicate external API issues.

5. **Transaction Duration**

   ```
   Query: db.transaction:true
   Metric: p90(span.duration)
   Threshold: > 300ms
   ```

   **Why**: Long-running transactions can cause lock contention and connection pool exhaustion.
</Steps>

<Aside type="tip">
**Alert Fatigue**: Start with higher thresholds and gradually lower them as you optimize. An alert that fires constantly will be ignored. Aim for alerts that indicate genuine issues requiring action.
</Aside>

## Building Performance Dashboards

Dashboards give you at-a-glance visibility into application performance trends.

### How to Create Dashboard Widgets

From any Trace Explorer query, click **Save As** > **Dashboard Widget**. Choose visualization type:
- **Time Series**: Trends over time (latency, throughput)
- **Big Number**: Current state (error rate, cache hit rate)
- **Table**: Top N slowest operations

### Essential Performance Dashboard Widgets

#### 1. API Endpoint Latency Overview

**Widget Type**: Time Series
**Queries**: Create separate series for each critical endpoint

```
Query 1: http.route:/api/products AND http.method:GET
Metric: p90(span.duration)
Label: "Products List"

Query 2: http.route:/api/orders AND http.method:POST
Metric: p90(span.duration)
Label: "Order Creation"

Query 3: http.route:/api/products/search
Metric: p90(span.duration)
Label: "Product Search"
```

**Why**: See all critical endpoints on one chart. Spot performance regressions after deployments.

#### 2. Database Performance by Table

**Widget Type**: Table
**Configuration**:
```
Query: span.op:db
Group By: db.table
Metrics:
  - p90(span.duration)
  - count()
Sort By: p90(span.duration) DESC
```

**Why**: Identify which tables are slowest and how frequently they're queried. Prioritize optimization efforts.

#### 3. Cache Hit Rate

**Widget Type**: Big Number
**Calculation**:
```
Query 1 (Hits): span.op:cache.get AND cache.hit:true
Metric: count()

Query 2 (Total): span.op:cache.get
Metric: count()

Formula: (Hits / Total) × 100
```

**Why**: Monitor cache effectiveness at a glance. Should be > 80% for product queries.

#### 4. Operation Type Breakdown

**Widget Type**: Time Series (stacked)
**Configuration**:
```
Query: span.op:*
Group By: span.op
Metric: avg(span.duration)
```

**Why**: See relative performance of HTTP requests, DB queries, cache operations, and external calls in one view.

#### 5. Slowest Transactions

**Widget Type**: Table
**Configuration**:
```
Query: (none - show all traces)
Columns:
  - Trace ID
  - http.route
  - span.duration
  - order.items_count (if available)
Sort By: span.duration DESC
Limit: 10
```

**Why**: Quickly identify the slowest recent transactions to investigate.

#### 6. Database Operations Trend

**Widget Type**: Time Series
**Queries**: Separate series for operation types
```
Query 1: db.operation:SELECT
Metric: count()

Query 2: db.operation:INSERT
Metric: count()

Query 3: db.operation:UPDATE
Metric: count()
```

**Why**: Understand your database load profile. Sudden spikes in INSERTs or UPDATEs may indicate issues.

#### 7. Request Throughput

**Widget Type**: Time Series
**Configuration**:
```
Query: http.method:*
Metric: count() per minute
Group By: http.route
```

**Why**: Monitor traffic patterns. Helps correlate performance degradation with traffic spikes.

#### 8. Cache vs Database Response Time

**Widget Type**: Time Series
**Queries**:
```
Query 1: cache.hit:true
Metric: avg(span.duration)
Label: "Cache Hit"

Query 2: span.op:db
Metric: avg(span.duration)
Label: "Database"
```

**Why**: Visualize the performance benefit of caching. Database should be 50-100x slower than cache.

<Aside type="note">
**Dashboard Organization**: Create separate dashboards for:
- **Executive View**: High-level metrics (error rate, P95 latency, throughput)
- **Engineering View**: Detailed performance by operation, table, endpoint
- **On-Call View**: Current alerts, recent errors, slowest transactions
</Aside>

## Understanding OTLP Span Attributes

When using OpenTelemetry with OTLP, your traces include rich attributes you can search:

**HTTP Attributes:**
```
http.method: GET, POST
http.route: /api/products, /api/orders
http.status_code: 200, 404, 500
http.request.method: GET (newer semantic convention)
```

**Database Attributes:**
```
db.system: postgresql
db.operation: SELECT, INSERT, UPDATE
db.statement: SELECT * FROM products WHERE id = $1
db.table: products, orders
```

**Custom Application Attributes:**
```
order.id: 42
order.user_id: 1
order.items_count: 3
order.total_amount: 459.97
payment.transaction_id: txn_123
cache.key: products:all
cache.hit: true/false
search.query: laptop
```

<Aside type="note">
**OTLP vs SDK**: With OTLP traces, you get full control over custom attributes but won't have automatic performance issue detection (like N+1 queries) that Sentry SDK provides. You'll need to identify patterns manually through queries and aggregations.
</Aside>
